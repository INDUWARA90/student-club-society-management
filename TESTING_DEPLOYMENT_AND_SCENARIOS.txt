1.1 TESTING PHILOSOPHY & STRATEGY
--------------------------------------------------------------------------------
The application utilizes a rigorous, multi-layered testing pyramid comprising:
- Service-level Unit Tests (with isolated mock dependencies)
- Security Filter Unit Tests (testing tokens, lockouts, and rate limits)
- Database-backed Integration Tests (running against a real MySQL 8.4 instance)
- Concurrency & Race Condition Tests (verifying pessimistic locks and transactions)
- Frontend Component & State Tests (React Testing Library, Vitest, Redux Toolkit)
- Static Code Analysis, Linter & Security Audit Gates (oxlint, npm audit, Trivy)

Total Test Volume:
- Backend: ~315 Unit and Integration Tests (32 test classes)
- Frontend: ~29 Unit and Component Test Suites

1.2 BACKEND TESTING ARCHITECTURE (SPRING BOOT & JUNIT 5)
--------------------------------------------------------------------------------
Frameworks: JUnit 5 (Jupiter), Mockito, Spring Boot Test, Spring Security Test,
AssertJ, Flyway, and MySQL 8.4 JDBC Driver.

A. Service Layer Unit Tests:
   Every business domain service is tested with Mockito mocks to verify business
   rules, validations, calculations, and exception handling without database overhead:
   - AuthServiceTest: Registration, login, password changes, token handling.
   - ClubServiceTest: Club creation, categorization, approvals, rejections, archiving.
   - MembershipServiceTest: Join rules, officer assignments, presidential transfer.
   - EventServiceTest: Scheduling, validation, date constraints, cancellations.
   - VenueServiceTest: Booking windows, conflict checks, utilization calculations.
   - AttendanceServiceTest: Manual/QR check-in rules, start/end cutoff validation.
   - CheckInTokenServiceTest: HMAC-SHA256 generation, time windows, constant-time match.
   - PaymentServiceTest: Simulated payment recording, fee escrow, cascade refunds.
   - CertificateServiceTest: Eligibility threshold calculation, PDF generation.
   - ClubExpenseServiceTest: Officer permissions, ledger aggregation, budget vs spend.
   - AnnouncementCommentServiceTest & EventCommentServiceTest: Comment threads.
   - CommentReportServiceTest: Moderation workflows, dismiss/delete actions.
   - NotificationServiceTest: Email preferences, daily digests, WebSocket triggers.
   - UserAdminServiceTest: Super Admin account management, role elevation.
   - AdvisorRequestServiceTest & AnalyticsServiceTest: Academic oversight.

B. Security & Filter Unit Tests:
   - JwtAuthenticationFilterTest: Tests token parsing, validation, and instant
     revocation when `issuedAt` is before `password_changed_at`.
   - LoginAttemptServiceTest: Tests 5-attempt brute-force counter, 15-minute
     lockout, unknown email locking, and cache cleanup.
   - RateLimitFilterTest: Tests sliding-window counter (10 req/min), HTTP 429
     trigger, and trusted vs spoofed `X-Forwarded-For` headers.

C. Real-Database Integration Tests (`*IntegrationTest.java`):
   Unlike simple in-memory H2 tests that hide MySQL-specific bugs, backend
   integration tests execute against a real MySQL 8.4 database:
   - `IntegrationTestBase`: Base class configuring the Spring Boot Test context.
     * Database Safety Rail: The base test runner inspects the target database URL.
       If the database name does NOT contain the substring "test", it immediately
       aborts to prevent touching development or production databases!
     * Wipes and resets the test database before each test run.
   - `WorkflowIntegrationTest`: Exercises multi-step end-to-end HTTP scenarios
     across MockMvc (registration -> approval -> event creation -> payment -> attendance).
   - `ConcurrencyIntegrationTest`: Spawns multi-threaded worker pools to stress-test
     concurrency:
     * 4 simultaneous RSVPs racing for the 1 remaining seat in an event (verifies
       pessimistic row locking `@Lock(LockModeType.PESSIMISTIC_WRITE)`).
     * Simultaneous presidential handoffs racing to ensure exactly 1 President exists.
   - `CatalogQueryIntegrationTest`: Tests SQL pagination, filtering, and `X-Total-Count`.
   - `SecurityIntegrationTest`: Full HTTP filter chain authorization sweep.
   - `UserAdminIntegrationTest`: Tests administrative user lifecycle.
   - `VerifiedRegistrationIntegrationTest`: Tests strict email verification mode.

1.4 HOW TO EXECUTE TESTS LOCALLY
--------------------------------------------------------------------------------
Backend Tests (Requires a running local MySQL instance):
  cd backend
  # Run all unit tests (fast, no DB required):
  ./mvnw test
  # Run all unit AND integration tests against MySQL (creates club_management_test):
  DB_USERNAME=root DB_PASSWORD=your_password ./mvnw verify

Frontend Tests & Audits:
  cd frontend
  # Run fast linter:
  npm run lint
  # Run all Vitest suites:
  npm test
  # Run with coverage:
  npm run test:coverage
  # Run production build check:
  npm run build
  # Run dependency vulnerability audit:
  npm audit

PART 2: HOW DEPLOYMENT WAS DONE / DEPLOYMENT ARCHITECTURE
################################################################################

The system supports two production deployment architectures:
1. Cloud-Native Split Architecture (Render API + Vercel SPA + TiDB/Aiven MySQL)
2. Azure Virtual Machine Container Stack (Docker Compose + Automated GitHub Actions CI/CD)

--------------------------------------------------------------------------------
2.1 CLOUD-NATIVE SPLIT ARCHITECTURE (RENDER + VERCEL)
--------------------------------------------------------------------------------
A decoupled architecture where frontend and backend scale independently:

```
[ Developer Git Push ]
        |
        +---> .github/workflows/backend.yml (Changes in backend/**)
        |       1. Starts MySQL 8.4 service container in GitHub Actions runner.
        |       2. Runs Flyway migrations from V1 to V4.
        |       3. Executes all ~315 unit & integration tests (`./mvnw verify`).
        |       4. Builds Docker container stamped with GIT_SHA commit hash.
        |       5. Pushes container to GitHub Container Registry (ghcr.io).
        |       6. Runs Aquasec Trivy security scan (fails on CRITICAL CVEs).
        |       7. Calls Render Deploy Webhook for the exact commit.
        |       8. Polls GET /api/health until status="UP" and version=commit.
        |       9. Executes live smoke tests (verifies 401s on private, 200 on public).
        |
        +---> .github/workflows/frontend.yml (Changes in frontend/**)
                1. Runs `oxlint`, Vitest test suite, and `npm audit`.
                2. On Pull Requests: Deploys preview instance to Vercel and comments URL.
                3. On Push to Main: Compiles production bundle with VITE_API_BASE_URL.
                4. Deploys to Vercel production edge CDN.
                5. Runs live smoke test verifying SPA routing and deep links.
```

Zero-Downtime & Rollback Safeguard:
- Render executes health checks against `GET /api/health`.
- If a new backend build fails to connect to the database or fails migrations,
  Render refuses to route traffic to the container and continues serving the
  previous working container.

--------------------------------------------------------------------------------
2.2 AZURE VIRTUAL MACHINE PRODUCTION STACK (DOCKER COMPOSE)
--------------------------------------------------------------------------------
For self-hosting on a single cloud server, the entire platform is deployed to an
Azure Virtual Machine managed by Docker Compose.

VM Topology:
- Azure VM: Ubuntu Server 22.04 LTS (Standard_B2s, 2 vCPUs, 4GB RAM)
- Swap Space: 2GB swapfile configured to prevent OOM during container start.
- Azure Network Security Group (NSG) Rules:
  * Port 22 (SSH): Management
  * Port 80 / 8080 (HTTP): Frontend Nginx container
  * Port 5000 (HTTP): Backend API container
  * Port 443 (HTTPS): SSL / TLS

Docker Compose Production Stack (`docker-compose.prod.yml`):
- `backend`: Spring Boot 3 container running on Java 21 non-root image.
  Configured with JVM memory limits: `-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0`.
- `frontend`: High-performance Nginx Alpine container serving optimized Vite SPA dist.
  Configured with SPA rewrite rules (`try_files $uri $uri/ /index.html =404;`).
- `mysql`: Official MySQL 8.4 LTS image with persistent Docker volume storage (`mysql_data`).
- `backup`: Alpine container running an automated backup cron service:
  * Executes daily automated database dumps (`mysqldump | gzip`).
  * Stores timestamped backups in `/backups/club_management-<timestamp>.sql.gz`.
  * Retention policy: Prunes old dumps, retaining the newest `BACKUP_KEEP=7` backups.
  * Restore script (`scripts/restore.sh`) enables one-command database recovery.

Automated Azure VM CI/CD (`.github/workflows/deploy-azure-vm.yml`):
- Triggered automatically on push to `main`.
- Step 1 (Build & Push): GitHub cloud runner builds multi-stage Docker containers
  for frontend and backend, tagging them with commit SHA and `:latest`, then pushes
  to GitHub Container Registry (`ghcr.io`).
- Step 2 (SSH Deployment): Using `appleboy/ssh-action`, the workflow connects via SSH
  to the Azure VM, authenticates to GHCR, pulls the newly built containers, runs
  `docker compose -f docker-compose.prod.yml up -d`, and polls `/api/health`
  until the service is fully operational.

--------------------------------------------------------------------------------
2.3 DATABASE MIGRATIONS ENGINE (FLYWAY)
--------------------------------------------------------------------------------
Schema evolution is 100% automated via Flyway migrations (`backend/src/main/resources/db/migration`):
- `V1__init.sql`: Core baseline tables (users, clubs, memberships, events, attendance).
- `V2__expenses_and_feedback.sql`: Financial ledger, expense tracking, star ratings.
- `V3__phase3_tables.sql`: Venues, resources, comment moderation, email tokens.
- `V4__add_active_to_users.sql`: User activation/deactivation flags for governance.

Rules:
- Flyway checks migration checksums at startup. Editing an already-applied migration
  file causes Flyway to fail loudly, preventing silent schema drift.
- JPA DDL Auto is locked to `validate` in production, ensuring Hibernate never alters
  tables behind Flyway's back.

--------------------------------------------------------------------------------
2.4 KEY CONFIGURATION ENVIRONMENT VARIABLES
--------------------------------------------------------------------------------
- `DATABASE_URL`: JDBC URL (e.g., `jdbc:mysql://host:3306/club_management?useSSL=true`)
- `DATABASE_USERNAME` & `DATABASE_PASSWORD`: MySQL credentials
- `JWT_SECRET`: 256-bit+ secret key for HMAC-SHA256 signing
- `SEED_DEMO_DATA`: `true` for local dev demo; `false` in production
- `REQUIRE_EMAIL_VERIFICATION`: `true` enforces email verification before actions
- `BOOTSTRAP_ADMIN_EMAIL` & `PASSWORD`: Creates initial Super Admin on first run
- `TRUST_FORWARDED_HEADERS`: `true` behind proxy; `false` standalone
- `CORS_ALLOWED_ORIGINS`: Comma-separated frontend domains
- `VITE_API_BASE_URL`: Public API endpoint used by React SPA

SECTION 1: AUTHENTICATION & USER ACCOUNT SCENARIOS
--------------------------------------------------------------------------------
1.1  Register New Student: Fresh registration creates account with role `STUDENT`,
     `email_verified=false`, and dispatches verification email.
1.2  Duplicate Email Registration: Re-registering existing email returns neutral
     HTTP 202 without creating duplicate, dispatching "already registered" alert.
1.3  Login Before Email Verification: Login succeeds; if verification is required,
     state-changing actions (joining, RSVP, payments) return 403 until verified.
1.4  Verify Email: Submitting valid token sets `email_verified=true`.
1.5  Resend Verification: Logged-in unverified user triggers fresh token email.
1.6  Expired/Invalid Verification Token: Using expired or altered token returns 400.
1.7  Login Success: Correct email/password returns valid JWT and profile.
1.8  Login Wrong Password: Bad password returns HTTP 401 Unauthorized.
1.9  Login Unknown Email: Non-existent email returns neutral 401 (no user leak).
1.10 Forgot Password (Known Email): Submitting registered email sends reset link.
1.11 Forgot Password (Unknown Email): Returns neutral 200/202 (anti-enumeration).
1.12 Reset Password: Using valid reset token sets new password; old password fails.
1.13 Reset Password Reused Token: Re-submitting already consumed token returns 400.
1.14 Get Current User: `GET /api/auth/me` returns authenticated user profile.
1.15 Unauthenticated Profile Request: `GET /api/auth/me` with no token returns 401.
1.16 Update Profile: Changing name updates all club rosters, comments, and posts.
1.17 Update Profile Image: Uploading base64 image persists and displays.
1.18 Change Password: Providing valid current password + new password updates hash.
1.19 Change Password (Wrong Current): Fails with HTTP 400/401.
1.20 Change Email: Changing email triggers re-verification flow.
1.21 Token Tampering/Expiry: Altered or expired JWT returns 401 on protected routes.
1.22 CORS Preflight: Browser OPTIONS request returns correct allowed origin headers.
1.23 Dynamic CORS Configuration: Allowed origins strictly match configured env.
1.24 Sliding-Window Rate Limiting: Sending >10 requests/minute to auth endpoints
     from same IP returns HTTP 429 Too Many Requests.
1.25 Rate Limit Isolation: Tripping auth rate limiter does NOT block browsing
     endpoints or authenticated profile routes.
1.26 Rate Limit Expiration: Waiting 60 seconds clears window, allowing requests.
1.27 Account Brute-Force Lockout: 5 consecutive failed logins lock account for
     15 minutes across all IPs. Unknown emails lock identically.
1.28 Session Invalidation on Password Change: Changing password in Browser A
     causes Browser B's next request to return 401 (JWT instantly revoked).
1.29 Session Invalidation on Password Reset: Resetting password via email link
     revokes all active browser sessions immediately.
1.30 Email Notification Opt-Out: Unticking "Email me my notifications" stops
     outgoing emails while keeping in-app bell notifications active.
1.31 Rate Limiter Spoof Defense: Spoofed `X-Forwarded-For` headers are ignored
     when `TRUST_FORWARDED_HEADERS=false`.
1.32 Error Sanitization: Malformed requests return clean 400/500 messages;
     internal Java stack traces and SQL syntax are never leaked.
1.33 Unverified User Gating: With email verification required, unverified student
     gets 403 on join club, RSVP, pay, or propose club.
1.34 Anti-Enumeration Identical Responses: Both registered and new emails return
     exact same 202 response on signup.
1.35 Daily Notification Digest: Subscribing to daily digest batches notifications
     into a single 18:00 UTC daily email.
